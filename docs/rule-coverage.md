## Implementation and validation

The original 68 rules came from the pinned `0.5.4-dev` backend used by Urwid `0.6.3-urwid-dev`. The XCCDF provides the official titles, CAT severities and check and fix references. The operational risk column describes the potential impact of proposed remediation. [0.5.4-dev source](https://github.com/aaronwagner26/rhel8-stig-assistant/blob/v0.6.3-urwid-dev/src/classic/rhel8-stig.sh) · [0.6.3 validation record](validation.md)

- **Attended module staging** covers 7 rules. The script assesses the module and may create a dedicated policy file for an eligible, unused module after individual approval. Reboot and any applicable boot-image work require an administrator. The supported restore removes only the unchanged file created by that run.
- **Attended file or metadata plans** cover 44 additional rules for supported local layouts. Status, dry-run and the full pre-approval apply preview show the proposed changes. Unchanged low-risk operations can share an attended bulk approval. Medium-risk, high-risk and revised operations need individual approval. A file transaction validates candidate content where a supported checker exists. Recovery can restore authorized file content or metadata within the verified operation's limits. Service, mount or boot activation requires the stated separate action and proof on the running system.
- **Attended native actions** cover 5 rules and journal the checked original and resulting state. Runtime activation and recovery limits are identified in each plan.
- **Evidence and administrator review** covers 12 rules. The script records the evidence available within its supported scope. An administrator resolves the stated site, applicability or effective configuration questions. Some checks can identify definite findings.

Fixture validation covered selected parsers using local files or mocked tools. The CLI and parser results belong to development validation. The 0.5.0-dev handlers require individual genuine RHEL integration validation. The scenarios named in the rows describe intended coverage.

For the seven kernel modules, an ISSO-documented operational requirement is an administrator decision. Unsupported layouts, already loaded modules, built-ins, conflicting directives and approved operational uses require review. The feasible change is a dedicated rule-owned `modprobe.d` file containing both the install denial and blacklist. Plan requires site confirmation that the module is unused. A newly installed file can be removed on rollback after checking its recorded identity and checksum. Changes to loaded modules or initramfs require separate recovery procedures. Test common module fixtures for absent settings, equivalent or stricter directives, conflicting options, hyphen/underscore aliases, loaded/built-in state, prior boot image contents, pending reboot, idempotent apply, rollback and refusal after intervening edits. A reboot is an administrator action. Verify effective rules and absence of a loaded module after activation.

Review any relevant initramfs and kdump configuration before scheduling activation. Red Hat documents separate steps for boot images that contain the affected module. [Red Hat kernel module guidance](https://access.redhat.com/kb/41278)
